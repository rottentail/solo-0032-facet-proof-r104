# Facet Proof 复杂渲染资源边界评测

本报告回答两个问题：

1. Facet Proof 的尺寸、面数、采样和 45 秒渲染预算，是否让**合法**渲染任务走到明确终态？
2. 取消或超时之后，是否还有**可审阅、可导出**的图版？

所有数据来自本机实测，原始记录在 `benchmarks/results/`，脚本在 `benchmarks/`，可复跑。数字只在本机、本负载模型下成立，不是对其他环境的保证（见第 9 节）。

## 1. 结论摘要

1. **存在无法成功的合法请求。** 当单个 64×64 高采样块本身需要超过 45 秒时（本机实测：80 个宽三角扇、40000 源面、512×512、samples=1，首块约 58–60 秒），块永远无法提交，每次重试都从头重算同一块。实测连续 5 次尝试后进度停在 **0/64 块**，曝光始终没有成功图版，额度 262144 单位一直被占用。**这是“合法但不可完成”，不是慢。** 见第 5 节。
2. **合法任务即便可完成，也常常需要多次重试。** 最大合法请求（40000 面、512×512、samples=2、小包围盒几何）需要 3 次尝试、累计 106 秒才成功；36000 面宽三角扇、256×256 需要 11 次尝试、累计 462 秒。单次 45 秒预算与 40000 面上限不匹配。宽三角形版本即使在 20 次尝试后也未跑完，见 5.2 的不可完成结论。
3. **终态语义是正确的。** 除上述活锁外，每个被观察的请求都会落到 `succeeded`、`failed` 或 `cancelled`；没有永久 `running`（租约过期路径除外，见 5.3）、没有伪造成功、失败后额度归还。
4. **超时或取消后没有可审阅图版。** 图版行只在全画布完整、未取消、租约有效时创建。失败/取消后 `/verify`、`/bundle`、`/pick` 全部不可用，只剩 `/progress` 的块水位。已提交的块留在内容寻址存储中，但不是图版。
5. **取消是“受理 + 异步确认”。** 运行中调用 `POST /cancel` 返回 `state="running"`，工作器在下一个检查点确认后才变 `cancelled`。实测受理 3–104 ms，确认 16–621 ms。取消受理后额度不立即归还，确认终态后才归还。
6. **接近完成的取消会丢弃全部结果。** 256/256 块已提交、只差下采样和编码时取消，仍得到 `cancelled`、无图版，768 个 tile 通道引用留在磁盘上且没有物理回收。这是规格要求的行为，但对操作者意味着“晚一点取消”等于“白算”。
7. **面数不是有效成本指标。** 19602 面网格 256×256 需 1.67 秒，4000 面宽三角扇需 36.6 秒。耗时由“三角形屏幕包围盒面积 × 逐像素着色”决定（拟合 R²=0.922）。
8. **资源额度不是内存上限。** 默认容量 4194304 高采样像素恰好允许 4 个最大画布同时被接受。实测单任务峰值约 97 MB、两个并发约 160 MB；额度不约束进程 RSS，服务也不限制并发 worker 数。
9. **活锁不是纯理论：它同时占用不可回收的持久资源。** 在 5.2 的实验中，被活锁的曝光始终停在 `queued`、占据 262144 单位额度；若不人工取消，后续同尺寸提交会被 `capacity_reserved` 拒绝。另需注意，取消是唯一的退出方式，因为失败之外的终止路径对 `queued` 曝光可用，对 `running` 曝光则要等确认。

## 2. 机器与测量方法

### 2.1 环境

| 项 | 值 |
|---|---|
| 内核 / 架构 | Linux 7.2.12 (OrbStack VM)，aarch64 |
| CPU | 10 逻辑核，cgroup `cpu.max = max 100000` |
| 内存 | 16,424,796 kB，cgroup `memory.max = max` |
| 磁盘 | overlay；评测后半段根文件系统被宿主其他工作负载占满（可用 <300 MB），基准改用 `/dev/shm`（7.9 GiB） |
| Python | 3.11.2 (GCC 12.2.0) |
| 提交 | `6ec166f`，工作树仅新增 `benchmarks/` |

磁盘耗尽曾导致一次 `unable to open database file` 崩溃。该次数据已丢弃；最终数据采集在 `/dev/shm` 上，磁盘压力不影响计时（见 2.3）。

### 2.2 测量项与开销

- **墙钟**：`time.monotonic()` 包住一次 `worker.run_one()`。
- **峰值内存**：`benchmarks/case_runner.py` 每个用例独立进程，用 `ru_maxrss`（内核高水位），避免同进程历史累积；基线 RSS 在提交前读取。
- **采样开销**：需要随时间观察的用例用 `lib.RssSampler` 每 20 ms 读 `/proc/self/status`。对照测量（5000 面 256×256，各 3 次）显示有无采样线程差异落在噪声内（0.79/0.85 s 对 0.85/0.79 s），故报告不为此加修正系数，但声明**精度不优于 5%**。
- **状态观测**：终态、`/progress` 块水位、`/resources` 额度、图版是否存在、`/verify` 与 `/bundle` 是否可用。
- **进程隔离**：每个扫描用例独立解释器；HTTP 场景启动真实 `python3 -m facetproof` 子进程并用 urllib 驱动。
- **干扰控制**：正式数据在无其他基准并发时采集。中途有三次测量与其他基准重叠（宽三角扇的长程重试、部分取消探测），数据明显偏慢且进度曲线不单调；这些批次已删除，**不用于任何结论**。报告只保留可复现脚本产出的结果。

### 2.3 负载模型

- `fan_mesh(n)`：中心加圆周的宽三角扇。每个三角形屏幕包围盒大，模拟“少量大面积三角形”的最坏情况。这也是活锁实验用的几何。
- `grid_mesh(n)`：均匀网格，包围盒小，模拟常见细分表面。
- 正交投影、`span=2.0`、eye `[0,0,5]`，48 面扇填满画布。
- 请求：`width`/`height` 64–512，`samples` 1–2。

**画布大小与可见面积分离实验**（5000 面网格、512×512、samples=1，只改正交 `span`）：

| 几何 | 请求 | 墙钟 s | 峰值 RSS MB |
|---|---|---|---|
| grid 5000 | 256×256 s1 | 0.816 | 34.4 |

## 4. 内存

固定 48 面几何，改变画布与采样（`memory_scaling.json`）：

| 高采样像素 | 墙钟 s | 峰值 RSS MB | Δ RSS MB |
|---|---|---|---|
| 4,096 | 0.102 | 18.3 | 0.5 |
| 16,384 | 0.284 | 19.1 | 1.3 |
| 65,536 | 0.915 | 22.0 | 4.1 |
| 262,144 (512² s1) | 3.721 | 33.4 | 15.6 |
| 262,144 (256² s2) | 3.441 | 26.7 | 8.9 |
| 1,048,576 (512² s2) | 13.554 | 52.4 | 34.6 |

单进程基础 RSS 约 17.8 MB。高采样通道约 24 字节/像素（f64 深度 8 + f32 颜色 12 + u32 编号 4），assemble 再分配整幅缓冲。面数也推高内存：19602 面 256×256 峰值 76.5 MB；40000 面规划阶段单独增长约 41 MB（`supplementary.json`，RSS 而非峰值，仅作量级参考）。

**并发**：两个最大画布任务双线程同时运行，峰值 159.7 MB、Δ 119.6 MB，均成功。
**额度**：默认 4194304 单位，恰好容纳 4 个 1048576 单位的最大画布。4 个并发执行按加性推算超过 300 MB，**但这是推算，未实测**；服务不限制同时执行的 worker 数。

## 5. 终态、超时与取消

### 5.1 正常超时后的收敛（`retry_march.json`）

36000 面宽三角扇、256×256、samples=1，每次失败后立即 `retry`：

| 尝试 | 墙钟 s | 已提交块 |
|---|---|---|
| 1 | 45.06 | 2/16 |
| 5 | 45.03 | 7/16 |
| 10 | 45.03 | 15/16 |
| 11 | 11.13 | 16/16 → succeeded |

累计 462 秒后成功，图版 `/verify` 通过。说明块进度确实可复用，**但代价是十余次全量重试**。

### 5.2 单块超过预算 → 永久无法成功（`livelock_real_run.json`、`tile0_threshold.json`）

`tile_renderer.render()` 只在整块光栅化完成后调用 `store.commit()`；45 秒检查点在 `rasterize()` 内部抛出，**未完成的块不留进度**。因此若单块耗时 > 45 秒，每次重试都重算同一块。

直接把 80 份 500 面宽扇平移，让最密的中心落在序号 0 的块：

| 源面数 | 首块耗时（单独光栅化） |
|---|---|
| 20000 | 29.6 s |
| 30000 | 42.7 s |
| 40000 | 57.7–68.8 s |

真实运行（不预填、不改内部状态），40000 面 512×512 samples=1：

| 尝试 | 墙钟 s | 已提交块 | 状态 |
|---|---|---|---|
| 1 | 45.02 | 0/64 | failed render_timeout |
| 2 | 45.02 | 0/64 | failed render_timeout |
| 3 | 45.04 | 0/64 | failed render_timeout |
| 4 | 45.02 | 0/64 | failed render_timeout |
| 5 | 45.02 | 0/64 | failed render_timeout |

最终 `state=queued`、无图版、额度 262144 仍被占用。30000 面版本同样无法推进（3 次尝试 8/64 且增长停滞）。

**结论：限制允许存在一个永远无法成功的合法请求，且它的重试是无限循环。** 这不是“慢”，而是终态不可达；服务不提供任何“尝试次数上限”或“注定失败”的判定。

### 5.3 取消时机（`cancel_sweep.json`）

| 取消延迟 s | 取消前状态 | 取消前块 | HTTP | 受理 ms | 取消后到终态 s | 结果 | 图版 |
|---|---|---|---|---|---|---|---|
| 0.0 | running | 0/0 | 200 running | 14 | 0.025 | cancelled | 无 |
| 0.2（已完成） | succeeded | 1/1 | **409** | — | — | succeeded | 有 |
| 0.5 | running | 0/16 | 200 running | 7 | 0.025 | cancelled | 无 |
| 1.5 | running | 1/16 | 200 running | 63 | 0.164 | cancelled | 无 |
| 5.0 | running | 2/16 | 200 running | 6 | 0.025 | cancelled | 无 |
| 10.0 | running | 238/256 | 200 running | 48 | 0.113 | cancelled | 无 |
| 11.5 | running | 254/256 | 200 running | 3 | 0.016 | cancelled | 无 |
| 12.5 | running | 256/256 | 200 running | 104 | 0.621 | cancelled | 无 |

- 受理即返回，**响应中的 `running` 只表示已登记取消意图**。调用方必须轮询到 `cancelled`。
- 完成后的取消返回 409，图版保留且可校验/导出/开 proof。
- 最坏确认延迟 621 ms，出现在最后一块刚提交、正在下采样和 PNG 编码时；`encode_rgb` 内部无检查点，最大画布编码实测 0.75–1.0 秒，因此确认延迟上界约 1 秒量级，**未做跨机器保证**。
- 取消成功后额度归零；取消后的曝光不能 `retry`（409），只能用新 `dedup_key` 重新提交，**且不复用旧块**（同指纹但新曝光从 0/16 开始）。

### 5.4 取消/失败后的产物

- 无 `plates` 行；`/bundle`、`/verify`、`/pick` 全部不可用。
- `/progress` 仍返回块水位（如 238/256、`complete=false`），但块不是图版。
- 空格至全部 256/256 块已提交时取消：`/maintenance/inspect` 显示 768 个 tile 通道引用、0 个图版；块保留在 CAS 中，服务无物理 GC。
- 进程被 SIGKILL 后：重启 + `recover` 把过期租约放回 `queued`，重试复用已提交块并成功（21/256 → 256/256），图版校验通过，额度归还。租约未过期时 `recover` 不动作，任务保持 `running` 直到 120 秒租约到期。

## 6. 稳定性与精度

| 用例 | 墙钟 min/mean/max s | 峰值 RSS min/mean/max MB |
|---|---|---|
| grid 19602 面 512×512 s2 | 12.29 / 13.47 / 14.99 | 97.1 / 97.1 / 97.1 |
| fan 1000 面 256×256 s1 | 9.67 / 10.08 / 10.63 | 25.3 / 25.5 / 25.6 |
| fan 48 面 512×512 s1 | 3.41 / 3.62 / 3.95 | 33.4 / 33.4 / 33.5 |

峰值 RSS 近乎不变（±0.3 MB），墙钟波动 ±5–10%。**距 45 秒边界 10% 以内的单次结果不可靠**；活锁结论建立在“单块 58–69 秒对 45 秒”这类 30% 以上的差距上，不受此影响。30000 面（42.7 秒）处于边界内，报告中只作为趋势，不作为判据。

## 7. 限制与终态的对应关系

| 问题 | 结论 | 证据 |
|---|---|---|
| 每个合法请求最终有终态？ | **否**：单块 >45 秒的请求永远 `queued`/`failed` 循环 | `livelock_real_run.json` |
| 超时后可继续？ | 可以，前提是每块 <45 秒；需显式 retry | `retry_march.json`、`maxlegal_grid_march.json` |
| 最大合法请求一次能完成？ | 否，小包围盒需 3 次；宽三角形不收敛 | 同上 |
| 活锁会阻塞其他提交？ | 会：占用 262144 单位额度，第 5 个最大请求返回 `capacity_reserved` | 手工复核 + `resources` 语义 |
| 超时/取消后有图版？ | 无 | `cancel_probe.json`、`http_probe.json` |
| 能导出？ | 否，`/bundle` 不可用 | 同上 |
| 取消立即停止？ | 否，异步确认 16–621 ms | `cancel_sweep.json` |
| 额度限制内存？ | 否，额度是像素工作量 | `thread_concurrency.json` |
| 小内存机器？ | 明确 `resource_failure`，额度归还，外部重试可复用块 | `memory_limit.json` |

小内存补充：RLIMIT_AS 40–64 MB 时任务以 `resource_failure` 结束；72–80 MB 时块已全提交但仍因内存失败；放开限制后重试复用块并成功，图版校验通过。

## 8. 复跑方式

```sh
export TMPDIR=/dev/shm   # 根文件系统空间不足时

python3 -m facetproof.demo --flow render-plates

python3 benchmarks/sweep.py              # 三维度扫描 → sweep.jsonl
python3 benchmarks/cancel_sweep.py       # 取消时机
python3 benchmarks/cancel_probe.py       # 取消/超时后的产物
python3 benchmarks/recovery_probe.py     # 崩溃与租约恢复
python3 benchmarks/concurrency_probe.py  # 多进程 worker 与存储增长
python3 benchmarks/thread_concurrency.py # 两线程并发最大任务内存
python3 benchmarks/memory_limit.py       # RLIMIT_AS 下的失败与恢复
python3 benchmarks/unrenderable_recovery.py  # 不可完成请求的取消与重提交
python3 benchmarks/tile_livelock.py      # 单块超预算的活锁（约 4 分钟）
python3 benchmarks/supplementary.py      # span 实验、小包围盒面数、规划器内存
python3 benchmarks/phase_profile.py '<json>'  # 单用例分段计时，见文件头说明
python3 benchmarks/bbox_correlation.py   # 成本代理拟合
python3 benchmarks/summarize.py          # 汇总表
```

`tile_livelock.py` 是最重要的复现：它不需要改内部状态，只用 80 个平移的宽扇和 5 次 `worker/step` + `retry` 就能看到 0/64 且永不成功。`results/livelock_30k.json` 来自同配置的 30000 面一次性运行，仅用于趋势。

## 9. 适用范围与不保证项

- **仅本机**：10 核 aarch64 OrbStack VM、CPython 3.11.2。换 CPU、换 Python 版本（纯 Python 光栅器对解释器版本敏感）、或启用不同编译选项都会改变绝对耗时。**“40000 面 512×512 在 45 秒内不可完成”是本机结论；更快的机器上首块可能低于 45 秒，活锁区间会移动而不是消失**——只要有请求落在“单块 > 预算”区间，活锁就仍然存在。
- **仅本几何**：宽三角扇是刻意的最坏情况。真实模型通常介于扇与网格之间。不要用网格的 3 次收敛推断所有 40000 面任务，也不要用扇的活锁推断所有任务。
- **未测**：4 个以上并发最大任务、8 光源上限、透视投影下的超大三角形、超过 120 秒的租约、跨机器时钟、网络文件系统上的 SQLite、`samples` 上限之外的未来配置。
- **未验证的推算**：4×最大任务并发内存按加性推算 >300 MB，未实测。
- **规格未承诺时延或内存**：报告中的“97 MB”“621 ms”是观测值，不是契约。规格承诺的是语义（终态、额度、取消不提交图版），而第 5.2 节显示即使语义层面也存在“终态不可达”的语义缺口。
- **测量开销**：RSS 采样线程 <1% CPU；独立进程启动与建库约 50–100 ms，含在墙钟内。
